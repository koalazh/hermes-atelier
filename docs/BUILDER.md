# Builder and approval

`atelier-builder` investigates the user, inputs, desired output, tools, data, Memory ownership, security boundaries, and acceptance evidence before generating anything. One Profile is the default. A split needs a concrete permission, durable knowledge, working-directory, resource, failure, evolution, reuse, or material context-quality boundary. Demonstration-only splits must be labeled and compared with the simpler single-Agent design.

Each build owns one exact draft directory and one `BUILD.md` contract with Original Request, Aligned Goal, Users and Inputs, Expected Output, Profile Boundaries, Tools and Data, Memory and Skill Ownership, HTTP Collaboration, Observability Needs, Acceptance Scenarios, Missing Real Integrations, Risks, and Status.

Builder can ask focused questions when missing information changes the goal or safety boundary. It creates a complete native Distribution for each Profile and stops at `AWAITING_APPROVAL`. Natural-language consent never changes backend state.

Approval validates that there is exactly one app, rejects symlinks and secret files, validates the no-workflow `app.yaml`, promotes it, installs Profiles, creates endpoints, starts Gateways, and registers a content-derived revision. A failure moves the promoted directory to ignored diagnostic storage and records `profile_install_failed`.

Reviewer cannot edit. After a completed Review, Builder works in another isolated draft and emits only `candidate.patch`. The backend rejects empty, corrupt, out-of-app, secret, runtime, core, Builder, or Reviewer paths. A legal patch can still be rejected by the human when it encodes a fixed workflow or exceeds the evidence.
