# Hermes Atelier：从产品化到 Skill-first 的转变记录

## 发生了什么

Hermes Atelier 最初试图解决 Hermes 应用的设计、实现、交付与验证问题。随着 V1、V2、V2.1 的演进，我们不断删除重复的 Runtime、状态机、编排与平台能力，希望把它收缩成一个更薄、更合理的产品。

但最终重新审视后发现，最核心的用户路径其实可以由一个简单 Skill 完成：

> 用户与当前 coding agent 对齐需求，生成 PLAN 与实现 handoff，然后由当前 coding agent 直接完成实现与验证。

此前的多轮“对抗性检视”主要在回答“这个产品怎样做得更好”，却没有优先回答“这个产品是否应该存在”。因此我们在错误前提下做了大量局部优化。

## 最终转变

Hermes Atelier 不再继续向 V3、V4 演进，也不再试图通过重构证明自身产品形态成立。

新的默认方向是：

* 以 Skill 作为主要入口；
* 当前 coding agent 默认直接实现；
* PLAN 与 handoff 作为冻结目标和恢复接口，而不是默认转交给其他 Agent；
* 优先复用 Hermes、Codex、Claude Code 的原生能力；
* 只有真实项目反复证明需要时，才提取少量确定性脚本或工具；
* 旧仓库作为研究性原型、设计实验和失败经验保留，不再持续产品化。

## 今后的设计原则

1. **先证明问题存在，再设计系统。**
2. **先尝试不做、Prompt、文档约定、Skill，再考虑脚本、Plugin 或独立产品。**
3. **强 Agent 能动态完成的工作，不应过早固化成长期系统。**
4. **相对变轻不等于足够轻；比较对象永远是最小可行替代方案。**
5. **“可选模块”同样有维护、理解和兼容成本。**
6. **优先复用持续升级的上游能力，不建立第二套 Runtime、生命周期或工作流。**
7. **抽象必须来自多个真实案例的重复痛点，而不是为了证明架构而制作的 Demo。**
8. **对抗性检视首先要拥有否决项目的权力，而不是只优化既定方案。**
9. **工程质量只能证明实现认真，不能证明产品有必要存在。**
10. **当删除整个项目不会阻止用户完成任务时，应优先选择更薄的形态。**

## 以后所有 Agent 项目的前置问题

在讨论架构之前，必须先回答：

* 这个问题真实发生过几次？
* 当前 coding agent 或 Hermes 原生能力为什么不能解决？
* 一个 Skill 是否已经足够？
* 删除这个项目后，用户究竟失去什么？
* 半年后上游 Agent 更强时，这个系统还剩下什么独立价值？
* 是否已经有至少三个真实案例证明需要公共抽象？

只有这些问题得到明确答案，才允许进入 schema、runtime、dashboard、workflow、release 或版本规划。

## 一句话结论

> 不再把“教 Agent 如何工作”轻易做成一个产品；默认先做 Skill，让不断升级的 Agent 完成工作，只把经过真实需求证明的稳定机制固化下来。

## 为什么不能直接断言 Skill 已经正确

当前已经有足够证据否定 Atelier 的产品化形态：核心用户路径与当前 coding agent 的能力重叠，Builder 引入额外上下文转移，App Pack、Assurance 和生命周期包装也尚未被真实需求证明必须成为通用产品。

但这不等于新的 Skill 设计已经有效。现在还没有三个真实 Hermes 应用证明它能稳定减少重复建设、降低错误或提高交付质量。Skill-first 只是成本最低、可逆性最高的下一项假设，不是已经成立的答案。

新 Skill 必须接受真实任务验证，也允许最终得出“这个 Skill 本身没有足够价值，应删除”的结论。旧 Atelier 的 App Pack Demo、示例或 smoke test 只能说明旧实现的结构或链路，不能替代新 Skill 的真实案例。

## 为什么使用独立仓库

新旧项目必须在以下边界上隔离：

| 边界 | Hermes Atelier | Hermes App Engineering |
| --- | --- | --- |
| 定位 | V2.1 产品化阶段的研究性原型 | 单 Skill、无 Runtime 的实验 |
| 依赖 | Python、Dashboard、App Pack、Assurance 与 release 实现 | 仅开放 Agent Skills 目录内容 |
| 安装 | 历史产品与开发工坊的安装路径 | 可单独放入目标 Agent 的 Skill 目录 |
| 验证 | 保留 V2.1 的测试与历史证据 | 由三个新的真实 Hermes 应用任务独立评估 |
| 删除权 | 删除旧仓库不应影响新 Skill | 删除新仓库不影响 Atelier 历史或已实现应用 |

独立仓库避免旧概念诱导新实验继续复用 Builder、App Pack 和生命周期，也防止 V2.1 的测试数量与工程完成度污染 Skill 的验证结论。新仓库是新的实验单元，不是新的产品层，也不是 Atelier successor。

## 归档后的重新开放条件

只有真实需求已经出现，并且具体问题无法由当前 coding agent、普通 Skill 或 Hermes 当前原生能力解决时，才可以从旧仓库参考或提取一段局部实现。

提取必须针对已经重复出现的确定性缺口，重新验证当前适用性，并保持独立删除。不得为了保住既有代码寻找需求，也不得重新开放整个 Hermes Atelier 产品路线。
